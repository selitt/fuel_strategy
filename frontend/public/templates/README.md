# Как подготовить внешнюю стратегию для «Контура»

Внешняя программа или автор стратегии передаёт **план решений ParticipantPlan**.
Сайт читает решения и рассчитывает их своей моделью. Python-код, ноутбук,
формулы Excel и собственный расчётный движок через импорт не исполняются.

## Начать с готового файла

| Файл | Назначение |
| --- | --- |
| [plan-empty.json](plan-empty.json) | Пустой план: заполните решения сами |
| [strategy-example.json](strategy-example.json) | Полный календарь 2035–2040, бронь, инвестиции и запас |
| [strategy-example.csv](strategy-example.csv) | Те же решения в табличном формате |

Заполненный пример — снимок `data/strategies/base.json` на момент добавления
шаблонов, преобразованный в ParticipantPlan с `plan_id=external-base-example`.
Это пример формата на основе встроенной «Базовой», не обещание оптимальности,
выполнимости в обоих сценариях или подтверждённых вероятностей успеха.
Пустой план также можно импортировать, но он не обеспечивает потребности.

На сайте откройте **Импорт файла**, выберите JSON/CSV/XLSX/XLS и нажмите
**Импортировать**. Можно выбрать несколько файлов: каждый станет отдельной
стратегией. Проверьте решения в редакторе, сохраните и рассчитайте план.
Просмотрите дефицит, ограничения, стоимость и результат для нужного сценария.
Успешный импорт проверяет структуру, а не экономическую допустимость.

В окне импорта доступны пустые CSV и XLSX. Для Excel скачайте XLSX, оставьте
лист `plan` и заполните его по таблице ниже. Либо перенесите в него строки
заполненного CSV. XLS поддерживается на входе, но отдельного шаблона XLS нет:
при сохранении из Excel сохраните имя листа `plan` и значения ячеек.

## JSON: контракт стратегии

```json
{
  "plan_id": "my-strategy-v1",
  "scenario_id": "BASE",
  "decisions": {
    "supply_orders": [
      {"year": 2035, "source_id": "A", "order_t": 10,
       "delivery_date": "2035-01-15", "batch_id": "a-2035-01"}
    ],
    "capacity_reservations": [
      {"year": 2035, "source_id": "A", "reserved_capacity_t": 10}
    ],
    "investments": [{"investment_id": "ZBO", "year": 2036}],
    "inventory_policy": {"initial_inventory_t": 0}
  }
}
```

Этот короткий пример показывает поля, но не покрывает весь спрос.
Для полного календаря используйте `strategy-example.json`.

| Поле | Что записывать |
| --- | --- |
| `plan_id` | Непустой идентификатор вашей версии стратегии |
| `scenario_id` | `BASE` или `MANDATORY_STRESS`, с таким регистром |
| `supply_orders` | Массив отдельных партий, не годовых итогов |
| `year` в партии | Год получения, целое число 2035–2040 |
| `source_id` | Код источника из таблицы ниже |
| `order_t` | Заказанный объём партии в тоннах, до потерь/надёжности |
| `delivery_date` | Дата получения `YYYY-MM-DD`, обязательна при положительном объёме |
| `batch_id` | Непустой уникальный во всём плане код положительной партии |
| `capacity_reservations` | Не более одной строки на источник и год; объём в `reserved_capacity_t` |
| `investments` | Не более одной строки на `investment_id`; `year` — год решения |
| `initial_inventory_t` | Физический запас на 1 января 2035, тонны; задайте явно |

Объёмы — конечные неотрицательные числа. В JSON используйте точку в дробях,
числа без кавычек, без `NaN`, `Infinity`, комментариев и повторных ключей.
Файл содержит один объект, а не массив стратегий и не оболочку `{"plan": ...}`.
Не передавайте `schema_version` и `project_id` в обычном плане: интерфейс
использует их для распознавания полного проекта.

## CSV, XLSX и XLS: одна таблица

Заголовок CSV (UTF-8, допустим BOM):

```csv
record_type,plan_id,scenario_id,year,source_id,order_t,reserved_capacity_t,investment_id,initial_inventory_t,delivery_date,batch_id
plan,my-strategy-v1,BASE,,,,,,,,
inventory_policy,,,,,,,,0,,
supply_order,,,2035,A,10,,,,2035-01-15,a-2035-01
capacity_reservation,,,2035,A,,10,,,,
investment,,,2036,,,,ZBO,,,
```

| `record_type` | Заполняемые колонки помимо `record_type` | Количество |
| --- | --- | --- |
| `plan` | `plan_id`, `scenario_id` | Ровно одна строка |
| `inventory_policy` | `initial_inventory_t` | Ровно одна строка |
| `supply_order` | `year`, `source_id`, `order_t`, `delivery_date`, `batch_id` | По строке на партию |
| `capacity_reservation` | `year`, `source_id`, `reserved_capacity_t` | По строке на источник и год |
| `investment` | `year`, `investment_id` | По строке на инвестицию |

Остальные ячейки строки оставляйте пустыми. Не дублируйте `plan_id` и
`scenario_id` в строках партий. Не добавляйте колонки с комментариями,
итоги, объединённые ячейки и формулы. Все 11 заголовков лучше сохранить;
для старых таблиц парсер допускает отсутствие двух последних, но положительные
партии без даты и кода расчёт не примет.

Разделитель CSV — запятая или `;`. Десятичная запятая поддерживается только
при разделителе `;`; проще использовать точку и не разделять тысячи пробелами.
В XLSX/XLS используется лист с точным именем `plan`; даты записывайте текстом
`2035-01-15`, а не числовой датой Excel. В XLSX формулы отклоняются;
для XLS тоже передавайте только значения, не полагайтесь на сохранённый
результат формулы. Переименование `.csv` в `.xlsx` не создаёт книгу Excel.

Лимит размера смотрите в окне импорта или `/api/meta` (`max_upload_bytes`);
стандартная настройка — 2 МиБ. Держите таблицу в пределах 10 000 строк
включая заголовок, ячейки — не более 10 000 символов.

## Правила, необходимые для расчёта

Текущие исходные мощности (сверяйте с `/api/catalog`, если набор данных менялся):

| Код | Название | Мощность, т/год | Условия |
| --- | --- | --- | --- |
| `A` | Earth-Core | 190 | Доступен с 2035 |
| `B` | Earth-Flex | 110 | Доступен с 2035 |
| `C` | Earth-New | 130 | Нужна инвестиция `EARTH_NEW` и завершение подготовки |
| `D` | Lunar-ISRU | 120 | Нужна `LUNAR_ISRU` до 2038; поставки с 2038 |
| `E` | Emergency | 80 | Доступен с 2035 |

Для заказов и брони принимаются и названия каналов. Используйте одно
обозначение последовательно; не смешивайте `A` и `Earth-Core` в одном году.
Сумма партий источника за год и бронь не должны превышать его мощность.
Для простого переносимого плана явно задавайте бронь не меньше суммы заказов
по каждому используемому источнику и году; резервирование влияет на стоимость.

Год партии должен совпадать с годом `delivery_date`. Модель использует
365 дней в каждом году: **29 февраля запрещено**. Дата означает получение,
а дату заказа модель вычисляет по сроку поставки; она может быть до 2035.
Для годового решения внешнего оптимизатора сформируйте несколько партий
с датами и сохраните точную сумму годового объёма после округления.

Для `EARTH_NEW` укажите год решения, например 2035: при исходном сроке
подготовки 24 месяца партия допустима с `2037-01-01`.
Для `LUNAR_ISRU` укажите финансирование не позднее 2037 и поставки с 2038.
Для модернизации склада используйте `ZBO` с 2036 или позже.
Примеры отдельных инвестиционных решений:

```json
[
  {"investment_id": "EARTH_NEW", "year": 2035},
  {"investment_id": "ZBO", "year": 2036},
  {"investment_id": "LUNAR_ISRU", "year": 2037}
]
```

Это значение `decisions.investments`, а не отдельный файл для импорта.
Добавление всех инвестиций не делает стратегию допустимой: проверяются также
бюджет, запас, обслуживание спроса и остальные ограничения модели.

## Изменение условий поставщиков — только JSON

Необязательный `source_overrides` находится рядом с `decisions`. Например,
добавьте в копию полного плана:

```json
"source_overrides": {
  "A": {"capacity_t_per_year": 180, "variable_cost_mln_per_t": 6.5}
}
```

Это фрагмент, не самостоятельный JSON. После снижения мощности скорректируйте
заказы и бронь. Здесь ключи — строго `A`–`E`, не названия каналов.
Пропущенные поля берутся из исходного каталога. Допустимые поля:
`capacity_t_per_year`, `variable_cost_mln_per_t`,
`reservation_rate_mln_per_t_year_capacity`, `take_or_pay_share`,
`lead_time_min_value`, `lead_time_max_value`, `lead_time_unit`,
`reliability_profile`, `available_from_year`.

Доля take-or-pay и вероятности — от 0 до 1. Сроки — целые неотрицательные,
минимум не больше максимума; единицы `month`, `week`, `day`.
Сохраняйте ключи исходного профиля надёжности, например `constant:0.96`
для A. `null` допустим только для неизвестного года доступности;
известный исходный год нельзя превратить в неизвестный.
Подробные типы даёт `/api/schemas/input`, дополнительные проверки выполняет
движок. Результат с overrides помечается `RESEARCH_SOURCE_OVERRIDES`:
это исследовательские допущения, не изменение исходного CASE_INPUT.
Табличный формат overrides не переносит; используйте JSON для такого плана.

## Как внешнему решению записать файл

Алгоритм оптимизации запускается у автора. Его выход — массивы решений
по описанному контракту. Пример сохранения в Python без библиотек проекта:

```python
import json
from pathlib import Path

# Начните с полного шаблона рядом со скриптом и замените решения
# результатами своего алгоритма, сохраняя обязательные поля партий.
plan = json.loads(Path("strategy-example.json").read_text(encoding="utf-8"))
plan["plan_id"] = "team-solver-v1"
plan["scenario_id"] = "BASE"
Path("my-strategy.json").write_text(
    json.dumps(plan, ensure_ascii=False, indent=2, allow_nan=False) + "\n",
    encoding="utf-8",
)
```

Загрузите `my-strategy.json` через сайт. Для сравнения сценариев создайте
копию с `scenario_id=MANDATORY_STRESS`, сохранив те же решения.
Не передавайте внутренние `annual_orders`, `volume_t` и `prefix` из
`data/strategies/`: импорт ожидает `decisions.supply_orders` с `order_t`,
датой и кодом каждой партии. Дополнительные JSON-поля могут сохраняться,
но это не означает, что модель использует их в расчёте.

## Схемы, API и остальные файлы

Пути ниже относятся к адресу запущенного сайта:

| Путь | Назначение |
| --- | --- |
| `/api/schemas/input` | Актуальная JSON Schema входного DTO, включая overrides |
| `/api/schemas/plan` | Более общая исходная схема организатора |
| `/api/schemas/result` | JSON Schema результата; не шаблон стратегии |
| `/api/schemas/export` | Исходная схема экспорта организатора |
| `/api/catalog` | Справочники и сценарии текущего набора |
| `/api/calc/template` | Пустой JSON-план |
| `/api/plans/import/template?format=xlsx` | Пустая книга с листом `plan` |
| `/api/plans/import/template?format=csv` | Пустой CSV |

`POST /api/plans/validate` принимает сам JSON-план в теле запроса,
`POST /api/plans/import` — multipart с полем `file`.
Оба проверяют структуру, не ограничения расчёта. Возвращается оболочка
с `plan`, `normalized`, `warnings`: для импорта нужен именно её объект `plan`.

Полный проект переносите через **Выгрузка → Выгрузить проект** и импортируйте
полученный JSON целиком. Не сочиняйте UUID, ревизии, хеши и сохранённые результаты:
для внешнего решения достаточно обычного плана. Экспорт результата JSON,
ZIP с результатами CSV и файлы сравнения сценариев не являются входными планами.

Исходные `demand.csv`, `supply_sources.csv`, `storage_options.csv`,
`investment_options.csv`, `constraints.csv` и YAML сценариев не загружаются
как стратегии. Они настраиваются в наборе данных проекта; импорт сайта
не заменяет справочники и не добавляет произвольные сценарии/источники.
JSON Schema — описание структуры, его тоже не загружают вместо плана.

## Если файл не принимается

| Симптом | Что исправить |
| --- | --- |
| 413 | Уменьшить размер/число строк, сверить лимит в `/api/meta` |
| 415 | Проверить формат и настоящее содержимое файла |
| 422 при импорте | Проверить JSON, заголовки, типы строк, числа и лист `plan` |
| Ошибка даты/партии при расчёте | Добавить дату, уникальный `batch_id`, согласовать год |
| Превышение мощности/брони | Сложить все партии по источнику и году; скорректировать решения |
| Источник не готов | Проверить инвестицию, год доступности и дату завершения подготовки |
| Расчёт получен, `is_feasible=false` | Изучить ограничения, дефицит и запас; формат может быть корректным |

JSON Schema и успешный импорт не доказывают выполнимость стратегии.
Математическая приёмка расчётного прототипа не завершена (`model_verified=false`).
