# 07 · W3 и команда: соединение, полный прогон и сервер

**Связь:** T06–T08. **Важно:** первый этап начинается с малых готовых частей, а не после всего backlog.

## Промпт агенту

Планируй интеграцию уже написанного коллегами, не переписывай их модули. Прочитай [маршрут](README.md), `AGENTS.md`, T06/T07/T08, G1_HANDOFF и последние передачи W1–W5. По умолчанию выдай ограниченный план и обнаруженные несовместимости. После разрешения выполняй только текущий этап. Не делай push или деплой на неизвестный сервер.

## Этап A → G2: один реальный сквозной пример

1. Получи согласованные commits W1/W2/W4 и API W3. Проверь контрактные версии до объединения. Чужой конфликт не исправляй выбором «оставить всё своё».
2. Возьми общий синтетический пример с независимым эталоном: изменить план → availability → physical → finance → checks → график/таблица → save → open → CSV. В каждом звене реальные вызовы; mock UI выключен.
3. Сверь баланс, деньги, units и каждую цифру CSV с сохранённым result. Изменение заказа должно менять результат; редактирование без расчёта оставляет статус stale.
4. Проверить нехватку/переполнение, ошибку API и два независимых запроса. Если не хватает данных/предположения, выводить это, а не зелёные проверки.

**G2:** участник, не писавший интеграцию, воспроизвёл путь. Не отмечать полные T02/T03/T06 готовыми только по маленькому примеру.

## Этап B: вся обязательная задача

- Прогнать V01–V10 через реальное ядро и дополнительную приёмку A01… из существующего каталога. Проверка идентификаторов в expected_checks.json не считается исполнением модели.
- Полный BASE и mandatory 2035–2040, все источники/опции/контракты, ежегодный service и резерв, внутригодовые capacity/inventory/timing, CAPEX, Emergency как основа, loss limit в stress. Не добавлять универсальный hard check нулевого дефицита.
- Сохранить результаты исследований W5: low/high, свои риски/меры, чувствительность/пороги, альтернативы и расширение. Отдельно зафиксировать реализованные и отсутствующие функции.
- Сверить код/интерфейс/выгрузки/записку. Проверить open/import после обновления/перезапуска, версионирование и отсутствие общих mutable-состояний между пользователями.

## Этап C: воспроизводимый запуск и деплой

1. Из чистого clone/распакованного snapshot выполнить documented setup с lock-файлами. Каждый участник проверяет свою ОС; W3 собирает матрицу Windows, macOS, Linux и CPU. Наличие Docker не является доказательством проверки всех платформ.
2. Предполагаемые команды после реализации соответствующих тестов/скриптов:

```text
uv sync --locked
uv run --locked pytest
uv run --locked ruff check src tests
npm --prefix frontend ci
npm --prefix frontend run api:generate
npm --prefix frontend run typecheck
npm --prefix frontend run test
npm --prefix frontend run build
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

Проверки, которым пока нечего запускать, отмечать отсутствующими, а не маскировать exit code. Существующие workspace-тесты запускать отдельно; они не подтверждают научные выводы.

3. Проверить два режима: native dev и Compose со статическим frontend/proxy. Убедиться, что API доступен через `/api`, healthcheck действительно выполняется, data volume переживает пересоздание. Не использовать `down -v`/prune для «починки» и не монтировать Docker socket в приложение. Compose должен запускать готовый образ без зависимости от IDE и локальной .venv. Для Apple Silicon не фиксировать amd64 без причины; серверную архитектуру проверять отдельно.
4. Для реального сервера получить у владельца адрес/ОС/архитектуру, разрешённый способ SSH, каталог и домен/существующий reverse proxy. Секреты не просить вставлять в репозиторий. Без этих сведений подготовить инструкцию, но не сообщать «задеплоено».
5. До публичного открытия: HTTPS либо существующий защищённый вход, оговорённый доступ жюри, backend только за proxy, отсутствие секретов в frontend, writable только data-dir, backup/restore volume и возможность отката образа. Собственные подписки и API-ключи эксперта не нужны. Не перезаписывать чужой proxy и не открывать лишние порты без согласия.
6. Провести тот же пользовательский путь на сервере и сохранить фактический протокол. Фиксировать commit и конфигурацию deploy; не менять приложение «на сервере руками» без отражения в коде.

## Что передать

Один интеграционный отчёт: commit, как повторить запуск, какие тесты выполнены, матрица ОС, фактический URL при наличии deploy, ограничения, оставшиеся вопросы. W5 получает только подтверждённые результаты для K01–K20/сдачи. Статус «полностью готово» без полного прогона и доказательств не использовать.
