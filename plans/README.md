# Пять участников с агентами: маршрут разработки

**Кейс:** «Топливный космоконтур 2035». **Дата:** 18.09.2026.
**Формат пакета:** только планы и промпты. Здесь нет кода приложения, установленных зависимостей, готовых расчётов или выбранной стратегии снабжения.

## Куда положить и что открыть

Добавьте папку `prompts/team/` в корень существующего проекта — рядом с `src/`, `frontend/`, `tasks/`. Не создавайте второй проект и не заменяйте весь прежний архив. Пакет добавляет девять Markdown-файлов; существующие файлы он не перезаписывает.

Откройте агенту **корень проекта**, не `fuel-hackathon/test_oil/`. Сначала каждый передаёт своему агенту [00_EACH_MACHINE.md](00_EACH_MACHINE.md). Общий фундамент делает **только участник W3** по [01_W3_FOUNDATION.md](01_W3_FOUNDATION.md). Остальные не создают параллельно свои package.json, uv.lock, API и календари.

В каждом промпте два режима: без слова «выполняй» агент даёт ограниченный план и останавливается; «выполняй ближайший этап этого файла» разрешает только описанный ближайший этап. Промпт не активирует остальные файлы. В этом чате подготовлены задания, а не их реализация.

## Стек и единые настройки

Пользователь выбрал Python + TypeScript + Docker; рабочий вариант последнего согласованного предложения — FastAPI, React/Vite, Plotly. Streamlit исключён. Ни стек, ни структура кода не являются требованиями организатора.

| Область | Выбранное направление |
|---|---|
| Backend | Python, FastAPI, Uvicorn, Pydantic, pydantic-settings |
| Данные и расчёты | NumPy, pandas, PyYAML; openpyxl для XLSX |
| Frontend | React + TypeScript + Vite, Plotly.js / react-plotly.js; Tailwind CSS для оформления |
| Проверки | pytest, HTTPX, Ruff; Vitest и Testing Library для компонентов |
| Типы API | Pydantic → OpenAPI → openapi-typescript; один источник схем |
| Запуск | Docker Compose: backend и frontend со статической сборкой и прокси `/api` |
| Сохранение | Для первой версии JSON-проекты и результаты в постоянном volume; без внешней SQL-базы |

**Предлагаемая базовая среда, не ранее утверждённые версии:** Python 3.12.x и Node.js 24 LTS. W3 проверяет совместимость, фиксирует точные patch-версии Python/Node, версию npm/uv и зависимости в одном общем изменении. Если версии уже согласованы и работают в репозитории, не заменять их молча. Node 24 на дату проверки — LTS; требования выбранного Vite/template тоже проверяются [S3–S4].

Используем `uv.lock` и `frontend/package-lock.json`. Остальные устанавливают через `uv sync --locked` и `npm ci`, а не заново подбирают версии [S2, S5]. Docker-образы также закрепляет W3. SciPy/оптимизатор, ML, Redis, Celery, Kubernetes и микросервисы **не входят в старт**; добавлять только отдельным обоснованным изменением.

## Очерёдность: всего три контрольные точки

**G0 — фундамент запускается.** W3 выполняет первый этап 01: среда, пакеты, React, FastAPI health, Docker. Каждый завершает вторую часть 00 на своей ОС. Зелёный health не означает работающую топливную модель.

**G1 — общий формат принят.** W3 завершает второй этап 01 вместе с W1/W2/W4: договорились о сущностях, единицах, календаре, диагностике и стыках. Зафиксировали commit с контрактом. Теперь 02–06 можно выполнять параллельно. До G1 W1/W2 готовят ручные примеры, W4 — пользовательский путь, W5 — источники и методику, без независимых реализаций общего формата.

**G2 — первый сквозной расчёт.** Соединить первые рабочие части по 07, не ждать готовности всей системы: ввод → реальное ядро → результат → сохранение → открытие → CSV. Затем полные правила 2035–2040, исследования и сдача. Автоматическая оптимизация не заменяет проверку заданного плана.

## Правила работы с агентами и ветками

Один агент — одна задача — собственный clone или worktree/ветка. Не запускать разных агентов в одной рабочей директории. Для каждой задачи сначала проверить `git status`, ветку и реальный код: после прошлого архива он мог измениться. Чужие незакоммиченные правки не трогать. Данные, секреты, локальные окружения и Node-модули не пересылать как способ синхронизации.

W3 согласует общие схемы и Python-зависимости; W4 владеет frontend после G0. Изменение API обсуждается с W4 и другими потребителями, затем схемы и типы обновляются одним согласованным изменением. Одновременно не редактировать общие lock-файлы. Интегратор объединяет небольшие проверенные части, а не пять гигантских веток в последний час. Push, установка с повышенными правами и деплой — только при разрешении владельца.

Каждая передача содержит: commit/ветку, изменённые файлы, версию контракта, команды и фактические результаты тестов, ещё не реализованное и следующий стык. Шаблон уже есть: [HANDOFF](../../docs/templates/HANDOFF.md). Проверку чужого изменения выполняет другой участник/агент; совпадение слов в отчёте не является тестом.

## Не создавать второй регламент

Существующие [tasks](../../tasks/README.md), [архитектура](../../docs/ARCHITECTURE.md), [правила](../../docs/regulation/RULES.md) и [приёмка](../../docs/ACCEPTANCE.md) сохраняются. Новые файлы — способ выполнения этих задач на выбранном стеке, не замена условий кейса. В старом каркасе `AGENTS.md` и metadata ещё говорят «стек не выбран»; **01 должен синхронизировать только действительно принятые решения**, не объявлять все вопросы закрытыми.

Обязательны материальный баланс, сроки/мощности, контракты, ёмкость, резерв, CAPEX, сервис и правильный стресс. `Deficit == 0` не универсальный hard check; 97%/99% обязательны в BASE и являются ориентирами в stress. Emergency ограничен именно как базовый канал. Потери ≤2% в stress с 2038 — проверка, не автоматическое изменение коэффициента. Полные основания — в `docs/Task/` и `fuel-hackathon/test_oil/`.
