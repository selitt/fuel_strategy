# 05 · W4: дашборд на React/TypeScript

**Связь:** T04. **Зависимость:** G0 для оболочки, G1 для форм и типов; живой расчёт — первые срезы W3/W1/W2.

## Промпт агенту

Планируй только интерфейс оператора для Python API. Стек React + TypeScript + Vite, Tailwind, Plotly.js/react-plotly.js; Streamlit/Next.js и второй backend не нужны. Прочитай [маршрут](README.md), `AGENTS.md`, T04, `docs/PRODUCT.md`, `contracts/` и G1_HANDOFF. Сначала предложи ближайший экран/срез; реализация после моего разрешения.

**Границы:** `frontend/` и фронтовые тесты. Общий API меняй только с W3. В этапе 01 W3 создал минимальную оболочку; не генерируй поверх неё новый проект. Npm-зависимости и package-lock меняет один владелец за раз.

## Первый срез

1. Получить исходный набор через API. Показать понятную форму маленького плана по общему контракту.
2. Отправить запрос и отобразить реальные результаты/диагностику. До готовности API использовать отдельный явно включаемый mock-режим с подписью «Синтетический пример, не расчёт»; production не подставляет mock при сетевой ошибке.
3. При изменении любого входа пометить результат «устарел, нужен пересчёт». Запоздавший ответ на предыдущий запрос не должен перезаписывать результат нового. Обрабатывать загрузку, отсутствие расчёта, ошибку и рассчитанный недопустимый план отдельно.
4. Подключить save/open и CSV через API для раннего сквозного среза.

## Четыре раздела продукта

**План:** источник, объём/дата заказа, резерв мощности, контрактный период, инвестиции, политика запаса. Явные CASE_INPUT/TEAM_DECISION/TEAM_ASSUMPTION. Контрольный набор не редактировать незаметно; исследования меняют копию с отдельным ID.

**Результаты и проверки:** временной график запаса, ёмкость, отметки годовых проверок 45-дневного резерва; спрос/served и дефицит; поставки по источникам; CAPEX/OPEX и остальные расходы. Таблица checks: правило, сценарий, период, объект, факт, порог, единицы, причина. Не сводить регламент к «шести галочкам» и не делать `Deficit == 0` универсальным hard check.

**Сравнение и риски:** несколько планов, BASE/mandatory, low/high и отдельные TEAM-сценарии. Дельты среды отдельно от изменения решения. Показывать настоящий вклад каждого риска/меры после появления расчётов W5; до этого явная недоступность функции.

**Проекты:** сохранить, открыть, копировать, импортировать и скачать CSV/XLSX. Готовность экспорта соответствует ревизии плана и результата.

Нужны подписи/единицы и читаемые таблицы, а не только цвет. Не требуется 3D-космос, регистрация пользователей или мобильное приложение. Графики строить из чисел API, формулы не переносить в JavaScript. `frontend/src/api/generated` создаётся из OpenAPI; не делать ручную копию финансовых DTO.

## Проверки и передача

Vitest/Testing Library: загрузка, ошибка API, invalid input, смена сценария, stale result после правки, гонка ответов двух запросов, признаки not_calculated/not_applicable, успешное сохранение/ошибка сохранения. Для связи с настоящим backend — совместная проверка W3 по 07. Минимальные команды: `npm --prefix frontend run typecheck`, `npm --prefix frontend run test`, `npm --prefix frontend run build`.

В отчёте: реализованные действия оператора, commit/версия API, команды/вывод, где ещё mock/недоступная функция, ссылка или скриншоты реально работающего интерфейса. Красивые фикстуры не являются доказательством правильности модели.
