# Контур · топливное планирование

Состояние на **19 сентября 2026 года**. Это одностраничное приложение для кейса «Топливный космоконтур 2035»: React/Vite frontend, FastAPI API, JSON-хранилище проектов и исходный расчётный движок.

Оператор может редактировать месячный календарь поставок с датами отдельных партий и инвестиции на 2035–2040 годы, загружать планы из JSON/CSV/XLSX/XLS, рассчитывать BASE и MANDATORY_STRESS, сравнивать одинаковые решения, сохранять проекты и выгружать JSON/CSV. Интерфейс и HTTP API работают. Математическая приёмка модели не завершена: API честно возвращает `engine.status=prototype` и `model_verified=false`.

Критические правила и ограничения расчёта собраны в [docs/MODEL.md](docs/MODEL.md). Рабочие входы, схемы и контрольные примеры находятся только в `data/`.

## Структура

- `src/engine/` — расчётный прототип;
- `src/app/` — FastAPI, DTO, проекты, импорт и экспорт;
- `frontend/` — React/TypeScript/Vite интерфейс и тесты;
- `data/` — CSV/YAML входы, JSON Schema и контрольные примеры;
- `docker/` — единственная production-сборка и Compose;
- `tests/` — Python, API, frontend delivery и tooling tests;
- `tools/` — генерация и проверка OpenAPI/TypeScript-контракта.

## Локальный запуск

Нужны Linux, Python 3.13, Node.js 22.12–24 и npm. Автоматическая подготовка устанавливает проектные зависимости и собирает frontend:

```bash
./scripts/prepare.sh
./run.sh local
```

Сайт откроется на <http://127.0.0.1:8080>. `run.sh local` использует только штатную Vite-сборку `frontend/dist`; если её нет, выполните:

```bash
npm --prefix frontend ci
npm --prefix frontend run build
./run.sh local
```

Для разработки с Vite proxy:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements/dev.txt
npm --prefix frontend ci
./run.sh dev
```

Frontend будет доступен на `http://localhost:5173`, API — на `http://127.0.0.1:8000`.

## Docker и GitVerse Cloud

Локальный сервер и облачная площадка используют один путь: `docker/Dockerfile` собирает Vite frontend, затем FastAPI обслуживает UI и API из одного контейнера.

```bash
./run.sh
```

При первом запуске терминал спросит логин, пароль и повтор пароля. Пароль при вводе не показывается. Выберите длинный уникальный пароль. Настройки сохранятся в `docker/.env` с доступом только владельцу файла; при следующих запусках вводить их заново не нужно. Ссылку вводить не требуется. Не отправляйте пароль в чат и не добавляйте `docker/.env` в Git. Для смены доступа отредактируйте `FUEL_HTTP_USER` и `FUEL_HTTP_PASSWORD` в этом файле и снова выполните `./run.sh`.

Файл `docker/.env` создаётся автоматически: вручную создавать его не нужно. Минимальной длины и требований к сложности пароля нет; логин и пароль должны быть непустыми, без управляющих символов, а логин — без двоеточия (требование HTTP Basic). Для автоматического запуска без терминала заранее задайте обе переменные доступа через окружение или `docker/.env`. Необязательный `FUEL_PUBLIC_ORIGIN` можно задать для дополнительной строгой проверки точного HTTPS-origin; обычному запуску он не нужен.

Контейнер публикует порт `8080`. В GitVerse Cloud/GigaIDE откройте этот порт как Public и используйте HTTPS-ссылку в отдельной вкладке. Docker и публичный launcher отказываются работать без настроенного доступа. Браузер попросит общий логин/пароль; все вошедшие могут редактировать общие проекты. Прямой публичный HTTP не поддерживается. HTTPS завершается на площадке, порт контейнера должен быть доступен через её защищённый прокси.

Изменяющие запросы браузера защищены проверкой `Sec-Fetch-Site`: разрешён `same-origin`, отклоняются `cross-site` и `same-site`. Без этого заголовка проверяется соответствие HTTPS Origin и Host; API-клиенты без обоих заголовков работают с тем же паролем. После 10 неудачных попыток входа за минуту адрес подключения временно получает `429` и `Retry-After`. Приложение не доверяет произвольному `X-Forwarded-For`; если площадка объединяет клиентов за одним адресом прокси, лимит будет общим для них. Проверить это нужно при развёртывании. `/api/health` остаётся открытым для healthcheck.

```bash
./run.sh status
./run.sh logs
./run.sh stop
```

Проекты хранятся в named volume `fuel-contour_project_data`. Не выполняйте `docker compose down -v`, если данные нужно сохранить. Один JSON-store рассчитан на один контейнер и один worker.

Одновременно выполняется один расчёт, ещё четыре могут ждать до 30 секунд. При переполнении очереди API отвечает `503` с `Retry-After: 5`. UI сохраняет предыдущий результат и сообщает об ошибке; бесконечного автоматического повтора нет. Обрыв HTTP-запроса не останавливает начавшийся расчёт, поэтому перед повтором сохранения откройте актуальную версию проекта.

## Резервные копии

Перед заменой или удалением проекта сохраняется предыдущая версия в `.backups/` внутри хранилища. Хранятся до 10 версий проекта, в том числе удалённого, и до 200 МиБ суммарно; старые копии удаляются при ротации. Если резервирование не удалось, изменение отменяется. Резервы внутри volume не защищают от потери самого volume — скачивайте архив перед обновлениями и после важных изменений.

Для локального хранилища остановите приложение и выполните:

```bash
.venv/bin/python tools/project_archive.py export --store .local/projects --output .local/projects-backup.zip
.venv/bin/python tools/project_archive.py restore --input .local/projects-backup.zip --store .local/restored-projects
```

Восстановление разрешено только в пустой каталог. Перед записью проверяются формат, контрольные суммы, размеры, безопасные пути и JSON всех проектов. Архив содержит проекты и их резервные версии, но не настройки доступа. Чтобы использовать восстановленный каталог локально, задайте `FUEL_DATA_DIR` равным его абсолютному пути перед запуском.

## Импорт планов

Кнопка «Импорт плана» принимает JSON, CSV, XLSX и старый бинарный XLS. JSON может содержать переносимый план или полный проект. Табличные форматы всегда создают несохранённый черновик плана и не заменяют справочники `data/`.

CSV и лист `plan` в Excel используют одинаковые колонки:

```text
record_type,plan_id,scenario_id,year,source_id,order_t,reserved_capacity_t,investment_id,initial_inventory_t,delivery_date,batch_id
```

Колонки `delivery_date` (YYYY-MM-DD) и `batch_id` необязательны при импорте старого файла, но нужны для расчёта положительных поставок. Год строки — год получения. Старые годовые объёмы сохраняются без автоматического распределения; даты назначает оператор в таблице месяцев. Модельный февраль всегда содержит 28 дней. Новый план загружает редактируемый стартовый пример из `data/monthly_start_plan.json`: 100 т Earth-Core в год распределены по 12 явно датированным партиям, бронь 120 т/год, ZBO с 2036, начальный запас 0. Это TEAM_DECISION_EXAMPLE, не найденная оптимальная стратегия. Существующие проекты не изменяются.

Допустимые типы строк: `plan`, `inventory_policy`, `supply_order`, `capacity_reservation`, `investment`. В файле должны быть ровно одна строка `plan` и одна строка `inventory_policy`. Готовые CSV/XLSX-шаблоны скачиваются рядом с формой импорта. CSV поддерживает UTF-8, разделители `,` и `;`, а при `;` — десятичную запятую. Формулы и неизвестные колонки отклоняются; дополнительные поля плана без потерь переносит только JSON.

Для Docker остановите сервис через `./run.sh stop`, затем создайте архив в volume и скачайте его:

```bash
docker compose --env-file docker/.env -f docker/compose.yaml run --rm --no-deps web python tools/project_archive.py export --store /data/projects --output /data/projects-backup.zip
docker compose --env-file docker/.env -f docker/compose.yaml cp web:/data/projects-backup.zip .local/projects-backup.zip
```

Каталог `.local` для скачивания должен существовать. Архив содержит пользовательские данные: храните скачанную копию вне публичного сайта. Обратное восстановление выполняйте той же CLI в остановленном окружении, указывая пустой каталог хранилища; не удаляйте действующее хранилище ради восстановления.

## Проверки

```bash
.venv/bin/python -m pytest -q --cov=src.app --cov-report=term-missing
.venv/bin/python tools/export_openapi.py --check
.venv/bin/python tools/generate_frontend_types.py --check
npm --prefix frontend test -- --coverage
npm --prefix frontend run build
.venv/bin/python -m pip install -r requirements/browser.txt
.venv/bin/python -m playwright install chromium
.venv/bin/python tests/web/public_smoke.py
docker compose --env-file docker/.env.example -f docker/compose.yaml config --quiet
```

OpenAPI хранится в `docs/api/openapi.json`, TypeScript-типы — в `frontend/src/api/schema.d.ts`. После изменения HTTP-контракта обновляйте их только штатными генераторами:

```bash
.venv/bin/python tools/export_openapi.py
.venv/bin/python tools/generate_frontend_types.py
```

Эти проверки подтверждают транспорт, хранение, сборку и согласованность контрактов. Они не доказывают математическую корректность модели или конкурсные показатели.

Отчёт Python охватывает `src/app`. Frontend coverage относится только к исполняемым в Node модулям `lib`/`api`, не ко всем React-компонентам и хукам. Отдельный Chromium smoke использует production-сборку, реальный API и временное хранилище: проверяет пароль, редактирование, сохранение, перезагрузку, конфликт двух вкладок и скачивание результата. Эти проверки и Compose config включены в CI; процентный порог покрытия не установлен.

## Известные границы

- модель использует 365 дней в каждом году;
- Monte Carlo использует реальные даты и объёмы партий и возвращает 100 дневных траекторий, диапазон 5–95% и распределение суммарного дефицита;
- пользовательские CSV/XLSX/XLS загружают решения плана, но не подключены как отдельный набор справочников расчётной модели;
- общий HTTP Basic-доступ не создаёт пользователей и ролей;
- автоматический оптимизатор и подтверждённая «лучшая стратегия» отсутствуют.
