# Контур · топливное планирование

Состояние на **19 сентября 2026 года**. Это одностраничное приложение для кейса «Топливный космоконтур 2035»: React/Vite frontend, FastAPI API, JSON-хранилище проектов и исходный расчётный движок.

Оператор может редактировать месячный календарь поставок с датами отдельных партий и инвестиции на 2035–2040 годы, загружать планы из JSON/CSV/XLSX/XLS, рассчитывать BASE и MANDATORY_STRESS, сравнивать одинаковые решения, сохранять проекты и выгружать JSON/CSV. Интерфейс и HTTP API работают. Математическая приёмка модели не завершена: API честно возвращает `engine.status=prototype` и `model_verified=false`.

Критические правила и ограничения расчёта собраны в [docs/MODEL.md](docs/MODEL.md). Рабочие входы, схемы и контрольные примеры находятся только в `data/`.

## Структура

- `src/engine/` — расчётный прототип;
- `src/app/` — FastAPI, DTO, проекты, импорт и экспорт;
- `frontend/` — React/TypeScript/Vite интерфейс и тесты;
- `data/` — CSV/YAML входы, JSON Schema и контрольные примеры;
- `docker/` — единственная production-сборка и Compose;
- `tests/` — Python, API, frontend delivery и tooling tests;
- `tools/` — генерация и проверка OpenAPI/TypeScript-контракта.

## Локальный запуск

Нужны Linux, Python 3.13, Node.js 22.12–24 и npm. Автоматическая подготовка устанавливает проектные зависимости и собирает frontend:

```bash
./scripts/prepare.sh
./run.sh local
```

Сайт откроется на <http://127.0.0.1:8080>. `run.sh local` использует только штатную Vite-сборку `frontend/dist`; если её нет, выполните:

```bash
npm --prefix frontend ci
npm --prefix frontend run build
./run.sh local
```

Для разработки с Vite proxy:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements/dev.txt
npm --prefix frontend ci
./run.sh dev
```

Frontend будет доступен на `http://localhost:5173`, API — на `http://127.0.0.1:8000`.

## Docker и GitVerse Cloud

Локальный сервер и облачная площадка используют один launcher: `docker/Dockerfile.frontend` собирает Vite frontend во временном контейнере, `run.sh` извлекает статические файлы, а `docker/Dockerfile` собирает итоговый FastAPI-образ. В рабочем окружении по-прежнему запускается один контейнер с UI и API; Node.js на хосте для Docker-запуска не нужен.

```bash
./run.sh
```

При первом запуске терминал спросит логин, пароль и повтор пароля. Пароль при вводе не показывается. Выберите длинный уникальный пароль. Настройки сохранятся в `docker/.env` с доступом только владельцу файла; при следующих запусках вводить их заново не нужно. Ссылку вводить не требуется. Не отправляйте пароль в чат и не добавляйте `docker/.env` в Git. Для смены доступа отредактируйте `FUEL_HTTP_USER` и `FUEL_HTTP_PASSWORD` в этом файле и снова выполните `./run.sh`.

Файл `docker/.env` создаётся автоматически: вручную создавать его не нужно. Минимальной длины и требований к сложности пароля нет; логин и пароль должны быть непустыми, без управляющих символов, а логин — без двоеточия (требование HTTP Basic). Для автоматического запуска без терминала заранее задайте обе переменные доступа через окружение или `docker/.env`. Необязательный `FUEL_PUBLIC_ORIGIN` можно задать для дополнительной строгой проверки точного HTTPS-origin; обычному запуску он не нужен.

Контейнер публикует порт `8080`. В GitVerse Cloud/GigaIDE откройте этот порт как Public и используйте HTTPS-ссылку в отдельной вкладке. Docker и публичный launcher отказываются работать без настроенного доступа. Браузер попросит общий логин/пароль; все вошедшие могут редактировать общие проекты. Прямой публичный HTTP не поддерживается. HTTPS завершается на площадке, порт контейнера должен быть доступен через её защищённый прокси.

Если вкладка GigaIDE «Облачные порты» не показывает принадлежащий Docker порт `8080`, запустите в отдельном терминале `python3 tools/cloud_port_proxy.py`. Появившийся пользовательский порт `8081` можно опубликовать в этой вкладке; терминал с прокси должен оставаться открытым. Прокси только передаёт TCP-трафик в приложение на `127.0.0.1:8080`, поэтому HTTP Basic-доступ остаётся обязательным.

Изменяющие запросы браузера защищены проверкой `Sec-Fetch-Site`: разрешён `same-origin`, отклоняются `cross-site` и `same-site`. Без этого заголовка проверяется соответствие HTTPS Origin и Host; API-клиенты без обоих заголовков работают с тем же паролем. После 10 неудачных попыток входа за минуту адрес подключения временно получает `429` и `Retry-After`. Приложение не доверяет произвольному `X-Forwarded-For`; если площадка объединяет клиентов за одним адресом прокси, лимит будет общим для них. Проверить это нужно при развёртывании. `/api/health` остаётся открытым для healthcheck.

```bash
./run.sh status
./run.sh logs
./run.sh stop
```

Проекты хранятся в named volume `fuel-contour_project_data`. Не выполняйте `docker compose down -v`, если данные нужно сохранить. Один JSON-store рассчитан на один контейнер и один worker.

Одновременно выполняется один расчёт, ещё четыре могут ждать до 30 секунд. При переполнении очереди API отвечает `503` с `Retry-After: 5`. UI сохраняет предыдущий результат и сообщает об ошибке; бесконечного автоматического повтора нет. Обрыв HTTP-запроса не останавливает начавшийся расчёт, поэтому перед повтором сохранения откройте актуальную версию проекта.

## Резервные копии

Перед заменой или удалением проекта сохраняется предыдущая версия в `.backups/` внутри хранилища. Хранятся до 10 версий проекта, в том числе удалённого, и до 200 МиБ суммарно; старые копии удаляются при ротации. Если резервирование не удалось, изменение отменяется. Резервы внутри volume не защищают от потери самого volume — скачивайте архив перед обновлениями и после важных изменений.

Для локального хранилища остановите приложение и выполните:

```bash
.venv/bin/python tools/project_archive.py export --store .local/projects --output .local/projects-backup.zip
.venv/bin/python tools/project_archive.py restore --input .local/projects-backup.zip --store .local/restored-projects
```

Восстановление разрешено только в пустой каталог. Перед записью проверяются формат, контрольные суммы, размеры, безопасные пути и JSON всех проектов. Архив содержит проекты и их резервные версии, но не настройки доступа. Чтобы использовать восстановленный каталог локально, задайте `FUEL_DATA_DIR` равным его абсолютному пути перед запуском.

## Импорт планов

### Несколько стратегий и сравнение

При открытии сайта доступны шесть готовых стратегий команды: «Земная крепость»,
«Лунный прорыв», «Сбалансированный контур», «Базовая», «Стресс-устойчивая»
и «Распределённый контур».
Их неизменяемые решения и явно заданные месячные партии находятся в
`data/strategies/` и доступны через `GET /api/calc/strategies`. Кнопка «Создать
свою на основе этой» открывает независимую редактируемую копию. Расчёты BASE,
STRESS и Monte Carlo не означают гарантированной надёжности или глобального
оптимума, пока математическая приёмка модели не завершена.

«Распределённый контур» — отдельное решение команды с диверсификацией поставок:
Earth-Core и Earth-Flex используются с 2035 года, Earth-New и Lunar-ISRU — после
подготовки и необходимых инвестиций. Emergency остаётся аварийным резервом.
Диверсификация является целью команды, а не дополнительным условием кейса;
снижение зависимости от одного канала само по себе не доказывает надёжность.
Результаты ограниченного поиска, BASE, обязательного стресса и сравнение
Monte Carlo со «Сбалансированным контуром» находятся в
`reports/diversified_strategy.json`. Отчёт содержит происхождение входов,
параметры поиска и фактически найденные нарушения; глобальная оптимальность
не заявляется.

Повторяемая подготовка только новой стратегии и её отчёта:

```bash
.venv/bin/python tools/optimize_strategy.py --archetype diversified --max-evaluations 10000 --seed 42 --output data/strategies/diversified.json --report reports/diversified_strategy.json
```

Этот вариант использует ограниченный поиск годовых объёмов и дат партий;
лимит включает оба детерминированных сценария. Финальная проверка и Monte Carlo
выполняются отдельно от поискового бюджета. Команда заменяет только указанные
файлы; пять исходных стратегий не переподбираются.

Опубликованный кандидат проходит проверки BASE без дефицита. В обязательном
стрессе он **не проходит** норму резерва на начало 2040 года: запас ниже нормы
на 38,97 т, суммарный дефицит за стрессовый горизонт — 79,4 т. В отдельной
BASE-выборке Monte Carlo (100 прогонов, seed 42) дефицита нет в 100 прогонах,
но все ограничения выполнены только в 86. Это результаты конкретной выборки,
а не гарантия надёжности.

Кнопка «Проверить Монте-Карло» под таблицей поставок запускает 100 прогонов
для выбранного сценария за весь горизонт 2035–2040. Результат открывается в
окне с дневными траекториями и распределением дефицита. «Посмотреть результат»
открывает уже выполненную проверку без повторного расчёта; изменение плана
или сценария отмечает её как устаревшую. Обычный пересчёт таблицы не запускает
Monte Carlo автоматически.

Месячные календари подготовлены отдельно от приложения: годовые объёмы каждого
канала, бронь, инвестиции и начальный запас сохранены. В одном месяце у канала
не более одной партии. Годовые строки `annual_orders` в файлах каталога фиксируют
исходные ограничения; расчёт и UI используют явные `supply_orders`.
Повторяемый подбор: `.venv/bin/python -m tools.prepare_strategy_calendars --write`.
Он ограничен 10 000 оценками на стратегию и не доказывает глобальную оптимальность.
Сравнение со старым равномерным календарём находится в
`reports/strategy_calendars.json`: первые четыре стратегии подбираются под BASE,
пятая — под MANDATORY_STRESS; обе оценки сохранены для каждой стратегии.
Приоритет — критический дефицит, общий дефицит, резерв, переполнение и потери.
Критический дефицит оценивается по опубликованному движком годовому уровню
обслуживания с точностью четыре знака, остальные показатели — по годовым балансам.
Старые проценты Monte Carlo и ранее сформированные отчёты не подтверждают новые
календари; в ходе их подготовки Monte Carlo не запускался.

Для поиска **новых** кандидатов `src/engine/optimize.py` и
`tools/optimize_strategy.py` используют `scipy.optimize.differential_evolution`.
SciPy должен быть установлен в среде запуска; при его отсутствии поиск завершается
с понятной ошибкой без автоматической подмены алгоритма. DE подбирает годовые
параметры, а декодер формирует явные месячные партии. Результат имеет формат
импортируемого плана `plan_id`, `scenario_id`, `decisions`; JSON можно открыть
через «Импорт файла» и сравнить с готовыми стратегиями. Эти инструменты не
перезаписывают каталог пяти готовых стратегий и не запускаются из UI.

Строка вкладок под шапкой хранит независимые стратегии. Через «+» можно создать
свою стратегию, открыть сохранённую или выбрать несколько JSON/CSV/XLSX/XLS-файлов.
Каждый файл открывается отдельной вкладкой; ошибка одного файла не отменяет
остальные загрузки. Свои стратегии редактируются; новые, импортированные и
открытые сохранённые стратегии автоматически добавляются к сравнению.
Прямая ссылка на сохранённый проект открывает его редактор рядом с готовым каталогом.

«Сравнить» открывает отдельный экран для двух и более выбранных вкладок без
искусственного ограничения количества, включая
несохранённые. Таблица показывает BASE и обязательный STRESS рядом; общий график
переключается между сценариями, дневным запасом, дневным дефицитом и годовыми
затратами. Компактная сводка размещает стратегии строками; «Подробнее» открывает
все показатели, а «Сравнивать с» добавляет разницу с выбранной стратегией.
Кнопка «Открыть» возвращает к стратегии с выбранным годом и сценарием.
Год поставок и год результата в редакторе синхронизированы; «К сравнению»
возвращает к прежнему выбору стратегий, года и графика. На настольном экране
от 1200×680 сравнение и редактор занимают высоту окна; длинная таблица поставок
прокручивается внутри своей панели. JSON/CSV сравнения содержит
снимки входов и признак актуальности каждого результата.

Изменённые решения пересчитываются автоматически общей последовательной очередью;
устаревшие результаты помечаются, сбой одного сценария не скрывает другой.
Импортированные результаты пересчитываются перед сравнением. Это не запускает
Monte Carlo и не подтверждает математическую приёмку модели.

Переключение вкладок сохраняет черновики в памяти. «Сохранить» записывает текущую
стратегию на сервер; закрытие вкладки не удаляет сохранённый проект. Несохранённые
черновики **не восстанавливаются после перезагрузки страницы** — браузер предупреждает
о них перед уходом. Сохраняйте нужные стратегии отдельно.

Кнопка «Импорт плана» принимает JSON, CSV, XLSX и старый бинарный XLS. JSON может содержать переносимый план или полный проект. Табличные форматы всегда создают несохранённый черновик плана и не заменяют справочники `data/`.

CSV и лист `plan` в Excel используют одинаковые колонки:

```text
record_type,plan_id,scenario_id,year,source_id,order_t,reserved_capacity_t,investment_id,initial_inventory_t,delivery_date,batch_id
```

Колонки `delivery_date` (YYYY-MM-DD) и `batch_id` необязательны при импорте старого файла, но нужны для расчёта положительных поставок. Год строки — год получения. Старые годовые объёмы сохраняются без автоматического распределения; даты назначает оператор в таблице месяцев. Модельный февраль всегда содержит 28 дней. «Создать свою» открывает пустой план без поставок, брони и инвестиций, с начальным запасом 0. Существующие сохранённые и импортированные проекты не изменяются.

Допустимые типы строк: `plan`, `inventory_policy`, `supply_order`, `capacity_reservation`, `investment`. В файле должны быть ровно одна строка `plan` и одна строка `inventory_policy`. Готовые CSV/XLSX-шаблоны скачиваются рядом с формой импорта. CSV поддерживает UTF-8, разделители `,` и `;`, а при `;` — десятичную запятую. Формулы и неизвестные колонки отклоняются; дополнительные поля плана без потерь переносит только JSON.

Для Docker остановите сервис через `./run.sh stop`, затем создайте архив в volume и скачайте его:

```bash
docker compose --env-file docker/.env -f docker/compose.yaml run --rm --no-deps web python tools/project_archive.py export --store /data/projects --output /data/projects-backup.zip
docker compose --env-file docker/.env -f docker/compose.yaml cp web:/data/projects-backup.zip .local/projects-backup.zip
```

Каталог `.local` для скачивания должен существовать. Архив содержит пользовательские данные: храните скачанную копию вне публичного сайта. Обратное восстановление выполняйте той же CLI в остановленном окружении, указывая пустой каталог хранилища; не удаляйте действующее хранилище ради восстановления.

## Проверки

```bash
.venv/bin/python -m pytest -q --cov=src.app --cov-report=term-missing
.venv/bin/python tools/export_openapi.py --check
.venv/bin/python tools/generate_frontend_types.py --check
npm --prefix frontend test -- --coverage
npm --prefix frontend run build
.venv/bin/python -m pip install -r requirements/browser.txt
.venv/bin/python -m playwright install chromium
.venv/bin/python tests/web/public_smoke.py
docker compose --env-file docker/.env.example -f docker/compose.yaml config --quiet
```

OpenAPI хранится в `docs/api/openapi.json`, TypeScript-типы — в `frontend/src/api/schema.d.ts`. После изменения HTTP-контракта обновляйте их только штатными генераторами:

```bash
.venv/bin/python tools/export_openapi.py
.venv/bin/python tools/generate_frontend_types.py
```

Эти проверки подтверждают транспорт, хранение, сборку и согласованность контрактов. Они не доказывают математическую корректность модели или конкурсные показатели.

Отчёт Python охватывает `src/app`. Frontend coverage относится только к исполняемым в Node модулям `lib`/`api`, не ко всем React-компонентам и хукам. Отдельный Chromium smoke использует production-сборку, реальный API и временное хранилище: проверяет пароль, редактирование, сохранение, перезагрузку, конфликт двух вкладок и скачивание результата. Эти проверки и Compose config включены в CI; процентный порог покрытия не установлен.

## Расчётный отчёт и чувствительность

[Отчёт по критериям кейса](reports/REPORT.md) связывает выводы с результатами
сравнения пяти стратегий, дополнительными стрессами, чувствительностью, реестром
рисков и интересами сторон. [Протокол проверок](reports/VERIFICATION.md) указывает,
что фактически запускалось и какие ограничения сохраняются.

Для воспроизведения JSON/CSV-пакета из текущих входов:

```bash
.venv/bin/python tools/analyze_case.py
```

Параметры исследований находятся в `data/analysis/config.yaml`. Цена Earth-Core
проверяется от 6 до 11 млн у.е./т с шагом 0,5 и исходной точкой 6,2; пороги
уточняются только в обнаруженных интервалах. Номинальное пересечение стоимости
отделено от выбора выполнимой стратегии. Ставка дисконтирования для базового
сравнения принята `r = 0` как `TEAM_ASSUMPTION`; показатель означает совокупные
затраты на обеспечение, а не прибыль. Сценарии исследований не перезаписывают
CASE_INPUT и не заменяют обязательный стресс. Скрипт обновляет расчётные файлы в
`reports/`; текст отчёта после изменения входов нужно сверить с новым манифестом.

## Известные границы

- модель использует 365 дней в каждом году;
- Monte Carlo использует реальные даты и объёмы партий и возвращает 100 дневных траекторий, диапазон 5–95% и распределение суммарного дефицита;
- пользовательские CSV/XLSX/XLS загружают решения плана, но не подключены как отдельный набор справочников расчётной модели;
- общий HTTP Basic-доступ не создаёт пользователей и ролей;
- оптимизатор не встроен в API/UI; отдельный экспериментальный поиск не доказывает глобальную оптимальность или подтверждённую «лучшую стратегию».
