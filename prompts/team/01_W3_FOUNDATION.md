## Этап A → G0: можно одинаково запустить у всех

1. Синхронизируй решение о стеке и форме интерфейса в `AGENTS.md`, `workspace.json`, `docs/decisions.json`, `START_HERE.md` и относящихся к ним карточках. Не помечай весь T00 завершённым: календарь, допуски, ставка, владельцы и сроки — отдельные решения. Старые исследовательские документы не переписывай как первоисточники.
2. Для исходного каркаса предлагается Python-пакет `src/fuel_planner/`. Перенеси смысловые README из `src/engine/physical`, `src/engine/economics`, `src/data_io` и других зон внутрь пакета без потери текста; обнови карты путей в tasks/index.json, tasks/team.json и документации. Если действующий Python-пакет уже есть, сохрани его и зафиксируй фактическую карту вместо второго пакета. До запуска 02–06 все получают одну карту.
3. Создай единый `pyproject.toml`/`uv.lock`, `.python-version` и `.node-version`; Node/npm также отрази в настройках frontend, версию uv — в SETUP. Runtime: fastapi, uvicorn, pydantic, pydantic-settings, numpy, pandas, pyyaml, openpyxl. Dev: pytest, httpx, ruff. Проверь совместимость и закрепи Python, uv, Node/npm; ориентиры 3.12.x/24 LTS — предложение пакета, а не повод менять уже рабочее согласованное окружение. Никаких глобальных pip-install для библиотек проекта.
4. С W4 создай минимальную React/TypeScript/Vite-оболочку. В существующую непустую папку не запускай генератор с удалением файлов. Один package-lock. Подключи Plotly и Tailwind без реализации экранов, проверь импорты. Добавь рабочие `typecheck`, `build`, `test` в npm scripts; `api:generate` добавь вместе с генерацией типов на этапе B. В стартовом UI только связь с API и честный статус готовности.
5. Подготовь `src/fuel_planner/adapters/api/app.py` с FastAPI и `GET /api/health`: статус процесса, версия приложения, признак `calculation_available=false`. Нельзя возвращать фиктивный успешный CalculationResult. Маршруты расчёта до реализации либо отсутствуют, либо явно отвечают NOT_IMPLEMENTED/501.
6. Создай Dockerfiles и `compose.yaml`: Python backend, production-сборка frontend, статический сервер/proxy `/api` к backend. Предлагаемый внешний локальный порт — 8080. В браузер не отправлять URL вида `http://backend:8000`. Для нативной разработки Vite proxy использует локальный backend. На сервере Vite dev server не запускать. Reference только для чтения; отдельный volume под сохранённые проекты; исходные `.venv`/node_modules в образ не копировать.
7. Документируй запуск в `docs/implementation/SETUP.md`: PowerShell и POSIX без обязательных bash/Make, нативный dev и одинаковый Compose, фиксированные версии и команды из 00. Добавь реальные smoke-тесты health/импортов. Не превращай «нет тестов» в зелёный job. Раздели workspace-проверки и тесты приложения.

**Особенность имеющегося каркаса:** один из `tests/workspace` проверяет `application_stack is None`. После подтверждённого выбора стека обнови только это устаревшее ожидание и статусные тесты; проверки исходных хешей/ссылок не ослаблять. `application_implemented` не выставлять true из-за health endpoint.

**G0 принят:** uv sync --locked, npm ci, импорты, typecheck/build, smoke и Compose реально работают; frontend получает health; после остановки/поднятия файлы volume сохраняются. Передай commit и короткие команды всем участникам; запиши фактические проверки Windows/macOS/Linux отдельно. Отсутствующая машина — «не проверено», не PASS.

## Этап B → G1: договориться о стыках, не писать модель

1. Вместе с W1/W2/W4 утверди CaseData, Plan, Scenario, AssumptionSet, CalculationRequest, CalculationResult, SavedProject, ConstraintCheck. Дополни исходные схемы, не редактируя `test_oil/schemas`. В Plan отдельно reserved/ordered/investments/physical reserve; в результате paid/delivered/served не объединять.
2. Зафиксируй в `contracts/` формат времени, порядок одновременных событий, границы года, единицы, precision/tolerance, сериализацию, статус неприменимых и невычисленных величин. Не назначай ставку, трактовку предстартовой доступности или вероятность отказа без основания/разрешения. Пробел источника блокирует зависимый расчёт, а не чтение CSV и работу над синтетическими примерами.
3. Согласуй независимые операции: применение сценария → договорная доступность → физическая история → финансы → объединение проверок. Конкретные сигнатуры запиши в `contracts/PIPELINE.md`, типы — в едином модуле `src/fuel_planner/domain/`; не передавай коллегам пустые dict без единиц.
4. Прочитай пять CSV и оба YAML через `src/fuel_planner/data_io/`, добавь структурные/межполевые проверки и происхождение данных. Не подменяй XLSX, которого нет. Тесты: неизвестный ID, negative/NaN/Infinity, critical > total, дубли, повреждённые файлы. Нарушающий мощность осмысленный план отличай от повреждённого JSON.
5. Зафиксируй Pydantic/OpenAPI и воспроизводимую генерацию TypeScript в `frontend/src/api/generated/`. Команда `api:generate` читает экспортированный локальный `contracts/openapi.json`; изменение типов не требует работающего сервера. Типы не являются клиентской runtime-валидацией или проверкой физики. Не добавляй API со «всегда успешными» ответами ради схемы.
6. Собери минимальный синтетический структурный пример для разработки с явной маркировкой, без конкурсной стратегии. Оформи `docs/implementation/G1_HANDOFF.md`: commit, версии, точные пути/сигнатуры, оставшиеся блокеры и согласованные предпосылки.

**G1 принят:** W1/W2/W4 подтвердили стыки; типы генерируются; загрузчик протестирован; опубликована одна версия контракта. Только затем запускать реализацию 02–06 параллельно. Фундамент не засчитывает математические V01–V10 или 20 критериев жюри.
