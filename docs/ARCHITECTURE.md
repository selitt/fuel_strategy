# Архитектура: что должно происходить, без реализации

**Статус:** смысловой каркас. Язык и форма UI согласованы как Python/FastAPI/Pydantic + React/TypeScript/Vite/Plotly; solver, календарь, ставка, точные допущения и финальная раскладка Python-пакета ещё не утверждены. См. [decisions.json](decisions.json).
Основание — [P1, с. 6–13](Task/Постановка_кейса_—_Топливный_космоконтур_2035_КосмоХакатон_2026.pdf) и [README test_oil, §24](../fuel-hackathon/test_oil/README.md).
Имена модулей и каталогов ниже — наше организационное соглашение, не дополнительные требования организатора.

## Полный путь

```text
Неизменяемые CASE_INPUT + версия источников
                     │
       План решений + сценарий + допущения
                     │
      Проверка структуры и смысловых связей
                     │
 Контракты и инвестиции → доступность мощности
                     │
 График заказов → поступления с учётом сроков/сценария
                     │
  Физический запас → потери → выдача → дефицит/сервис
                     │
 Платежи по заказам/обязательствам + хранение + CAPEX/OPEX
                     │
 Проверки ограничений → единый результат с происхождением
                     │
 Интерфейс · сравнение · сохранение/открытие · CSV/XLSX
                     │
 Чувствительность · собственные риски · меры · доказательства
```

Порядок выше объясняет зависимости, но не диктует отдельные проходы алгоритма.
В событийной реализации поставки, выдача и изменения хранилища могут обрабатываться совместно.
Платёж зависит от заказа и договора, а не только от полученного топлива.

## Разделение ответственности

| Область | Получает | Возвращает | Не делает |
|---|---|---|---|
| `contracts/` | Правила источников и решения T00 | Согласованные версии форматов/единиц | Не выбирает стратегию |
| `src/data_io/` | CSV, YAML, JSON, версии | Проверенные исходные сущности | Не меняет CASE_INPUT |
| `src/engine/physical/` | График доступности/поставок, спрос, режим хранения | История запаса, потери, выдача, дефицит | Не придумывает оплату |
| `src/engine/economics/` | Контракты, решения, сроки и физическая история | Обязательства, денежные потоки, экономические проверки | Не создаёт топливо деньгами |
| `src/engine/` | Входы всех блоков | Единый результат и проверки | Не рисует UI |
| `src/experiments/` | Явные варианты среды и планов | Сопоставимые запуски/последствия/пороги | Не заменяет BASE |
| `../src/app/persistence` | План, входы, допущения, версии | Сохраняемый и восстанавливаемый проект | Не теряет настройки |
| `src/reporting/` | Тот же результат ядра | Переносимая выгрузка/данные отчёта | Не пересчитывает математику второй раз |
| `src/adapters/` | Запрос интерфейса/CLI | Вызов ядра и понятный статус | Не дублирует бизнес-логику |
| `frontend/` | Контракты ввода/вывода | Рабочее место оператора | Не выдаёт фикстуры за расчёты |

Физический модуль получает контрактно допустимую доступность, а экономика — его историю запаса для holding cost.
Эти два направления в T01 согласуют стык вместе. Один участник не создаёт свою независимую версию календаря.

## Общие сущности

[contracts/README.md](../contracts/README.md): CaseData, Plan, Scenario, AssumptionSet, CalculationRequest,
CalculationResult, SavedProject. Это смысловые названия; конкретные поля/типы закрепляются в T01.

План и сценарий различаются: **план — наши действия, сценарий — условия расчёта**.
Изменение плана не маскируется как эффект стрессового сценария.
Каждый запуск должен иметь восстанавливаемые входы, идентификаторы, версию модели и допущения.

## Правила соединения

Одна расчётная логика для всех поставщиков и сценариев; особенности каналов представлены данными и явно описанными правилами.
Один набор результатов для интерфейса, сравнения и экспорта.
Бизнес-проверки выполняются до и во время расчёта: одной JSON Schema недостаточно.

Понятная диагностика содержит код/правило, сценарий, план, период, фактическое значение, порог, единицы и причину.
Отделять: неверный ввод; пока не рассчитано; рассчитанный, но нарушающий ограничения план; корректный расчёт.
Нет формулы/данных — нет права показывать нулевой риск или зелёный сервис.

## Первый интеграционный срез

После T01 направления T02/T03/T04 совместно определяют небольшой синтетический пример с независимым ручным эталоном.
Как только их первые совместимые части готовы, проверяется путь загрузка→изменение→расчёт→показ→сохранение→открытие→экспорт.
Это ранняя контрольная точка T06, а не ожидание готовности всех функций.
Синтетический пример не заменяет полные BASE/STRESS и научное обоснование.

## Границы этого архива

Здесь нет app.py с фиктивными ответами, псевдорасчёта, выбранного поставщика, оптимальных закупок или настроенного production API.
`tools/workspace.py` проверяет только комплект и навигацию.
Схема модулей не доказывает выполнение критериев: доказательства появятся после реализации и проверенных запусков.
