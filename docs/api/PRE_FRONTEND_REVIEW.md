Scope: проверить текущий backend, исправить ошибки веб-границы и тестами зафиксировать поведение. Сам frontend и математические модели не реализовывались и не переписывались.

## Итог

**Базу можно использовать для первого frontend-прохода по существующему API.** До изменений проходили 106 тестов. После исправлений проходят **146 тестов**, в том числе 40 новых проверок. Дополнительно выполнено 33 запроса к отдельному процессу Uvicorn с настоящим TCP/HTTP, проверены CORS, перезапуск и сохранность проектов.

Это подтверждает проверенные веб-сценарии, но не математическую корректность, конкурсную приёмку или готовность к публичному многопользовательскому размещению.

## Какие ошибки исправлены

### 1. Обход строгого JSON без Content-Type

В этой версии FastAPI тело без заголовка Content-Type разбиралось как JSON, а промежуточный слой выполнял строгую проверку только при явно указанном JSON-типе. В результате повторяющиеся ключи молча перезаписывались, а `NaN`/`Infinity` в дополнительных полях могли попасть в обработчик.

Проверка теперь охватывает и отсутствие заголовка. Корректный JSON без Content-Type по-прежнему принимается; недопустимые значения возвращают `422 VALIDATION_ERROR`. Для frontend всё равно следует явно передавать `application/json`, кроме FormData.

### 2. Потеря NaN/Infinity до проверки результата

На установленной версии Pydantic подтверждено: `model_dump(mode="json")` превращал нечисловое значение в дополнительных полях в `null`. Проверка после такой сериализации уже не видела ошибку. При повторном расчёте повреждённый ответ мог заменить предыдущий результат.

Проверки плана, шаблона и результата перенесены на Python-представление **до** JSON-сериализации. Невалидный ответ адаптера даёт `500 CALCULATION_FAILED` либо `INVALID_SERVICE_RESULT`; предыдущие результат и ревизия сохраняются. Обычный JSON `null` и строка `"NaN"` остаются допустимыми данными.

### 3. Ошибочный ввод давал внутренний 500

Подтверждены отдельные случаи: целое число длиной 5000 цифр, слишком глубокая вложенность, непарный Unicode-суррогат в дополнительном поле или имени ключа. Исправлена обработка исключений JSON и проверка структуры до сериализации. Такие HTTP-запросы и загруженные планы теперь получают `422`, а не внутреннюю ошибку.

Добавлены ограничения веб-структуры: глубина плана/результата — до **128**, полного JSON-документа — до **192** (корень имеет глубину 0). Разница оставляет место под оболочки проекта, снимок запуска и метаданные экспорта. Это транспортные ограничения, не изменение формул или расчётных DTO. В тесте проверен полный цикл с 120 вложенными массивами, кириллицей и emoji: сохранение → расчёт → открытие → экспорт → импорт.

## Что учитывать при написании frontend

Источник типов — `docs/api/openapi.json`. Исходный `KosmoAPI.yaml` содержит только две расчётные операции и не описывает весь веб-слой. В `frontend/` ещё нет package.json, React-компонентов и клиента API; текущий Compose запускает только backend.

Первый сквозной путь уже обеспечен ручками: шаблон/импорт → проект → редактирование → сохранение → расчёт → результат → сравнение → выгрузка. Годовые таблицы можно строить по `yearly_balance`, `source_schedule`, `financial_breakdown`, `constraint_checks`; значения берутся с сервера.

Для изменений и расчёта использовать последнюю `revision` как `expected_revision`. Обрабатывать `not_calculated`, `current`, `stale`, а также `409 REVISION_CONFLICT`. Импортированный результат имеет `origin=imported`: совпадение входов не подтверждает происхождение чисел. При ошибке сохранять введённые данные в UI; не подставлять нулевой результат.

Файлы отправляются через FormData, поле `file`, без ручного Content-Type. Импорт поддерживает JSON, **не CSV/XLSX как вход модели**. `GET /api/catalog` — справочник исходников, не API смены расчётного набора. Идентификаторы источников и инвестиций должны следовать согласованному адаптеру, а не догадкам клиента.

`inventory_trace` и `risk_register` текущего прототипа пусты: показывать отсутствие данных, а не нулевые риски или придуманный график. `prototype/unverified` остаются видимыми. Расчёт синхронный: допустим индикатор ожидания, но нет серверных процентов прогресса или фоновой очереди.

Полнота математической модели, V01–V10 и конкурсные критерии не проверялись. Docker/Compose не запускались: в среде нет Docker. Браузерной проверки React-приложения нет, потому что оно ещё не написано. Авторизация, многопроцессное хранилище и публичное размещение остаются вне scope.
