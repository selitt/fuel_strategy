# be0h + Вася: граница работы и следующий этап

## Одна система, не три отдельных backend

```text
Три участника: математические модули и предметная валидация
                             ↓
Вася: расчётные DTO + адаптер get_template_plan / calculate
                             ↓
be0h + Вася: стык CalculationBackend / обработка ошибок / версия
                             ↓
be0h: FastAPI → проекты, файлы, сохранение и экспорт → frontend
```

Сейчас это одно Python-приложение с подключением математических модулей внутри процесса. Отдельный HTTP-сервис для каждого блока не требуется. Универсальность означает заменяемый адаптер и описание структуры через DTO/OpenAPI, а не отмену типов и передачу неподтверждённых чисел в произвольном JSON.

## Ответственность

| Владелец | Что делает | Чего не делает в этой роли |
|---|---|---|
| Три участника модели | Формулы, календарь, данные для расчёта, ограничения, финансовые и риск-расчёты, контрольные примеры | Не дублируют API/экспорт/страницы UI |
| Вася | `src/app/dto/calc_dto.py`, `src/app/service/calc_service.py`, базовый `KosmoAPI.yaml`; собирает модули в один контрактный адаптер | Не обязан писать frontend и проектное хранилище |
| be0h | `src/app/api/`, веб-DTO, проектные сервисы и JSON-store, загрузка/выгрузка, OpenAPI для UI, CORS, запуск, весь `frontend/` | Не меняет `src/engine/`, математические DTO и формулы без согласования |

Совместно меняются только вход/выход адаптера, публичная диагностика и версия контракта. Чтобы не конфликтовать, Вася не правит проектные роутеры при изменении формул; be0h не редактирует `calc_dto.py` под удобство экрана. Если меняется схема, сначала согласовать её с обоими потребителями, затем обновить OpenAPI и тесты.

## Что исправлено в этой передаче

Восстановлен штатный `main.py` после конфликта слияния; Hello не возвращён. Сохранены две расчётные операции и все существующие веб-операции. Единый формат ошибок отражён в OpenAPI. Публичная ошибка адаптера не превращается в необъяснимый `500`; отсутствие шаблона/расчётного сервиса обозначается `503`. Для внедряемого адаптера можно передавать идентификатор/версию, от которых зависит актуальность сохранённого результата.

Backend ставится и проверяется без готового React-проекта. Обновлены навигация, фактические пути задач и инструкции. Удалять старые источники и переписывать модель для этого не потребовалось. Подробный результат проверки — [HANDOFF](HANDOFF.md).

## Последовательность работы

### 1. Принять одну рабочую базу

Передать изменения в командный репозиторий после сверки `git status` и diff,
сохранив работу коллег и завершив Git-конфликты в своей копии. Запустить тесты
и API по [API_README](../../API_README.md). Не заменять существующий `.git` или
submodule-каталоги распаковкой поверх рабочей директории.

### 2. Согласовать с Васей то, что должен уметь первый экран

Текущие DTO достаточны для годового редактора плана, проектов и годовых таблиц. Новые исходные наборы, тарифы, источники и периоды должны попадать в расчёт через согласованный контракт; сейчас такой общий input-flow не реализован. Не делать красивую кнопку загрузки CSV/XLSX, которая сохраняет файл, но не влияет на модель.

Для `inventory_trace` и `risk_register` Вася совместно с моделистами определяет строки, единицы и диагностику. До этого экран показывает «нет рассчитанных данных», а не подставляет нули. Межполевые ограничения/доступные идентификаторы проверяются в модели или её адаптере; frontend не вводит собственную математическую трактовку.

### 3. Работать параллельно

Вася подключает результаты трёх участников к адаптеру, не меняя проектные HTTP-операции. be0h делает React/TypeScript/Vite-приложение и API-клиент по `docs/api/openapi.json`. Начать со сквозного действия, а затем оформлять полноценный интерфейс: создать/импортировать → отредактировать → сохранить → рассчитать → показать результат → сравнить → скачать.

Первый UI использует `/api/meta` и `/api/catalog`, умеет показывать ошибки, загрузку, пустые таблицы, статус prototype и устаревший результат. Типы не копируются вручную из Python: схема — исходная точка для генерации клиента/типов. Сам генератор и frontend-манифесты относятся к следующему этапу и пока не созданы.

### 4. Совместно проверить пользовательский путь

Один и тот же результат должен отображаться на экране и попадать в выгрузку. После изменения входов старый расчёт становится stale. После перезапуска сохраняются проекты. Неподключённая математика возвращает явную ошибку, а не фиктивный успех. Сравнение использует сохранённые результаты; выбор оптимального плана остаётся задачей модели/анализа, не случайным правилом UI.

После появления frontend добавить его сервис/сборку в Compose и проверить реальный запуск обеих частей. Существующий Compose поднимает только backend; контейнер UI в этой передаче не добавлялся.

## Не включаем сейчас

Не переписываем математическую модель. Не создаём отдельный «универсальный движок», регистрацию, Redis, WebSocket, очередь работ, автоматический оптимизатор и новую базу данных. Проценты прогресса не рисуем для синхронного расчёта. Исходные схемы организатора и контрольные данные остаются неизменными.
