# Топливный космоконтур — структура проекта и следующий шаг

**Команда: 5 человек. Дата: 18.09.2026.**
**Статус: предложение архитектуры для согласования, не уже реализованное приложение.**

Кейс уже выбран: «Топливный космоконтур 2035». Повторный выбор кейса не нужен. Этот документ дополняет `docs/00_FUEL_CASE_BRIEF.md`, а не заменяет постановку организатора. Локальное состояние проекта известно из переданного отчёта Луны; URL репозитория команды и незакоммиченные изменения независимо не подтверждены.

## 1. Что делать сейчас

Сначала обеспечить воспроизводимую передачу материалов всей команде и согласовать границы модулей. Затем сделать один маленький сквозной расчёт, проходящий от ввода до выгрузки. После этого расширять охват и работать параллельно по пяти направлениям.

Не начинать пять независимых приложений, не искать новый кейс и не устанавливать произвольные технологии по совпадению названия Fuel. Fuel Labs, Sway, блокчейн и кейс «Космос как инфраструктура» к нашему продукту не относятся.

Есть две поправки к отчёту Луны:

- В `src/` находится код, но конкретные заказы, резервы и инвестиционные планы должны храниться отдельно, например в `plans/`. Допущения и настройки — в `configs/`.
- В обязательном стрессе повышение переменных цен Earth-Core/Earth-Flex на 25% действует только в **2038–2039**; в **2040** цены возвращаются к исходным. С **2038** действует ещё и предел `losses / throughput <= 0.02`. Это проверка, а не команда автоматически заменить коэффициент потерь на 2%. Основание: постановка, с. 7 и таблица с. 10.

## 2. Сначала исправить переносимость исходников

По отчёту Луны, каталоги `fuel-hackathon/test` и `fuel-hackathon/test_oil` записаны как вложенные репозитории без корневого `.gitmodules`. Перед изменениями агент должен подтвердить это локально, а не принимать отчёт за актуальное состояние.

Минимальные команды проверки из корня проекта:

```bash
git status --short
git ls-files --stage -- fuel-hackathon/test fuel-hackathon/test_oil
git -C fuel-hackathon/test_oil status --short
git -C fuel-hackathon/test_oil rev-parse HEAD
```

Также проверить существование и содержимое `.gitmodules`, фактические remote и доступность нужного commit. Команды относятся к уже существующим каталогам; отсутствие каталога — отдельный результат проверки.

Предлагаемый вариант для хакатона — **обычный неизменяемый снимок материалов** в `reference/test_oil/`, отслеживаемый основным Git как файлы. Не submodule и не копия с вложенной `.git`. Это наш выбор организации проекта, не требование кейса.

Сохранить исходный URL, фактический upstream commit и контрольные суммы импортированных файлов в `reference/source.lock.json`. Содержимое исходников не править; если локальные файлы уже отличаются от upstream, сохранить различия отдельно и явно описать происхождение снимка.

Перед переносом сохранить рабочие изменения и вложенную историю вне перемещаемых каталогов. Не удалять `.git` вслепую, не выполнять `reset --hard`, `clean -fd` или массовый `rm -rf`. Сначала создать и проверить копию; затем убрать только подтверждённые лишние ссылки из индекса. Чужие изменения не перезаписывать.

`test` не должен участвовать в импортах, сборке или расчётах. Исходную копию можно оставить вне рабочего дерева как архив. Ничего ценного из неё не удалять без сохранения.

Альтернатива — корректно оформить submodule с `.gitmodules`, URL и фиксированным commit. Не смешивать её со снимком. Для команды и передачи на GitVerse предлагается снимок: после обычного клонирования материалы уже должны быть на месте.

**Критерий результата:** после сохранения изменений в отдельной ветке обычный свежий clone этой ветки содержит все пять CSV и оба YAML. Старые локальные каталоги не должны маскировать неполную передачу.

## 3. Стек: принятое решение команды от 18.09.2026

Команда выбрала: **Python — расчёты, FastAPI + Pydantic — API и контракты, React + TypeScript + Vite + Plotly — интерфейс**. Docker Compose используется для воспроизводимого локального запуска; JSON — для сохранения проектов, CSV/XLSX — для выгрузки. Один backend и один frontend; отдельные микросервисы не нужны для первой версии.

Streamlit не входит в стартовый вариант. Не разрабатывать два интерфейса или второй backend параллельно.

В обоих вариантах предлагается начать с JSON-проектов и CSV-выгрузок, без обязательного сервера SQL. JSON хранит воспроизводимый проект; CSV служит требуемой табличной выгрузкой. При нескольких пользователях проекты и результаты разделять по идентификаторам, не сохранять всем один `current_plan.json`.

Версии среды, зависимости и способ установки зафиксировать после проверки выбранного стека и фактических окружений участников. Наличие Python в служебном CI организатора не означает, что он предписан участникам. C++, ML, оптимизатор, Docker, Redis и GPU не включать только ради названий технологий.

## 4. Предлагаемое дерево

Для выбранного стека ниже приведена организационная карта; точная раскладка Python-пакета остаётся открытой до G0:

```text
project/
├── README.md                         # что работает и как воспроизвести
├── AGENTS.md                         # правила для всех кодовых агентов
├── pyproject.toml                    # Python-пакет и зависимости
├── reference/
│   ├── source.lock.json              # источник, commit, хеши
│   └── test_oil/                     # неизменённые материалы организатора
├── configs/
│   ├── app.yaml                      # пути и настройки запуска
│   ├── assumptions.yaml              # явные допущения модели
│   └── scenarios/                    # только сценарии TEAM_*
├── plans/                            # сохранённые решения команды
├── src/
│   └── fuel_planner/
│       ├── models.py                 # общий формат данных, плана, результата
│       ├── data_io/                  # загрузка и проверка CSV/YAML/JSON
│       ├── engine/
│       │   ├── calendar.py           # модельное время и порядок событий
│       │   ├── contracts.py          # единая трактовка обязательств
│       │   ├── supply.py             # доступность и фактические поступления
│       │   ├── inventory.py          # потери, выдача, запас, дефицит
│       │   ├── finance.py            # платежи, CAPEX/OPEX, дисконтирование
│       │   ├── checks.py             # сбор проверок физических/денежных лимитов
│       │   └── evaluate.py           # сборка единого расчёта
│       ├── experiments/              # сценарии, сравнение, чувствительность, риски
│       ├── persistence/              # сохранение и повторное открытие проектов
│       ├── reporting/                # экспорт уже рассчитанных результатов
│       ├── api/                      # маршруты, без копий расчётных формул
│       └── cli.py                    # запуск ядра без интерфейса
├── frontend/                         # React-приложение и его lock-файл
├── tests/
│   ├── unit/                         # формулы и отдельные правила
│   ├── integration/                  # полная цепочка и BASE/STRESS
│   └── fixtures/                     # синтетические примеры с ручным эталоном
├── results/                          # отобранные воспроизводимые результаты
├── docs/
│   ├── 00_FUEL_CASE_BRIEF.md         # уже подготовлен
│   ├── Топливный_кейс_разбор_материалов.md
│   ├── architecture.md              # после согласования архитектуры
│   ├── data_contract.md             # поля, единицы, обязательность, версии
│   └── submission/                  # итоговые материалы для жюри
└── scripts/                         # проверенные команды запуска и проверок
```

Это целевая карта ответственности, а не приказ сейчас создать десятки пустых файлов. Файлы добавляются вместе с работающим поведением. В Python-пакетах предусмотреть необходимые `__init__.py`; дерево опускает служебные файлы для читаемости.

Исходные BASE и MANDATORY_STRESS читать из `reference/test_oil/scenarios/`. Не создавать вторую вручную редактируемую контрольную базу. Для исследовательских изменений использовать производный набор с ссылкой на исходник, отметками происхождения и явными отличиями.

Вариант Streamlit с отдельным `src/fuel_planner/ui/` не является принятым стартовым маршрутом; package layout уточняется на G0.

## 5. Согласовать общий формат до параллельной реализации

Главный договор команды: **исходные условия + решения + сценарий + допущения → единый результат расчёта**.

| Сущность | Что содержит |
|---|---|
| CaseData | Спрос, каналы, хранилища, инвестиционные опции, ограничения, единицы, версия исходников |
| Plan | Заказы, даты, резерв мощности, инвестиционные действия, начальный запас, политика выдачи |
| Scenario | Выбранное окружение и изменения параметров; не скрытая смена самого плана |
| Assumptions | Не заданные организатором соглашения, их основание и область действия |
| CalculationResult | Баланс и запас по времени, обслуживание, дефицит, расходы, проверки, происхождение расчёта |
| ExperimentResult | Набор запусков, сравнение, количественные последствия рисков и мер |

`schema_version`, идентификаторы проекта/плана/запуска и версия исходников должны позволять восстановить расчёт. В сохранённом запуске нужны снимок решений и допущений, а не только ссылка на изменяемый текущий план.

Согласовать имена и единицы до написания модулей: например, `reserved_capacity_t_per_year`, `ordered_t`, `delivered_t`, `served_t`, `cost_mln`. Не назвать одновременно мощность в т/год и объём в тоннах полем `reserve`.

Схемы организатора — основа обмена, но внутренности объектов придётся определить команде. Не путать прохождение JSON Schema с проверкой сроков, баланса и финансовых ограничений.

Расчётное ядро не зависит от React, FastAPI, Streamlit или HTTP. Интерфейс, API, CLI и экспорт используют один путь расчёта. Экспорт не вычисляет стоимость заново. Ввод с неправильным типом или неизвестным источником отличается от корректно описанного, но неисполнимого плана; последний должен давать численные нарушения, а не ложный статус «успех».

До параллельной работы отдельно согласовать календарь учебного года в 365 дней, порядок событий на границах периода, перевод месяцев, диапазоны lead time, подготовительный период и учёт начального запаса. Неопределённости не разрешать независимо в разных модулях. Основание требований: постановка, с. 6–9.

## 6. Предварительные пять направлений

Это распределение областей, не назначение людей: навыки участников и срок сдачи ещё не сообщены.

| Направление | Основная ответственность | Проверяемый результат |
|---|---|---|
| 1. Поставки и физическая модель | Календарь, доступность, поступления, потери, запас, выдача, физические ограничения | Выявляются внутригодовые дефициты, нарушения сроков, резерва и ёмкости |
| 2. Контракты и экономика | Общая трактовка контрактов, резервирование, take-or-pay, инвестиции, платежи, денежные ограничения | Нет двойного учёта; стоимость зависит от решений и дат по правилам кейса |
| 3. Интеграция и данные | Общие модели, загрузка, API/CLI, сборка расчёта, сохранение, экспорт, проверка запуска | Проект воспроизводится из чистого клона; результат проходит всю цепочку |
| 4. Интерфейс | Редактор плана, обзор, графики, сравнение, ошибки, сохранение/выгрузка | Пользователь работает без правки кода и без помощи разработчика |
| 5. Эксперименты и обоснование | Сравнение стратегий, sensitivity, собственные риски и меры, источники, координация материалов защиты | Эксперименты воспроизводимы; последствия выражены в тоннах, сроках и расходах |

Каждый пишет тесты своего модуля и описание своих формул. Пятый участник не является единственным тестировщиком или автором всех документов. У общего `models.py`, схем и интеграционных точек должен быть один согласующий; изменения форматов не проводятся незаметно для остальных.

Не делить людей «один делает BASE, другой STRESS» — это создаёт два расчётных ядра. Не делить по поставщикам с отдельными копиями формул. Каналы — строки данных в общей модели.

## 7. Ближайшие результаты, а не сразу весь хакатон

**Сначала — воспроизводимая основа.** У всех после клонирования одинаковые материалы; понятный README; выбран один стек; согласованы формат входа/выхода и соглашения по времени. Проверяется загрузка пяти CSV и двух YAML. Отдельно отмечаются открытые вопросы к организаторам.

**Затем — один сквозной мини-пример.** Маленький синтетический набор с независимо посчитанным ожидаемым результатом проходит загрузку, план, расчёт, проверки, показ в интерфейсе, сохранение, повторное открытие и CSV-экспорт. Изменение допустимого параметра действительно меняет результат. Невыполненные части не заменяются фиктивными числами. Это проверка интеграции, не готовое решение 2035–2040.

**После — весь обязательный охват.** Реальные входы кейса, подготовительный период, 2035–2040, все каналы и инвестиционные опции, контрольные V01–V10 через своё ядро, собственные граничные и интеграционные тесты. Сравнить исходный план в BASE, те же решения в MANDATORY_STRESS и явно изменённый план. Показать low/high demand, чувствительность, собственные риски и меры, перспективный период и дополнительный источник на копии набора.

**Затем — защита.** Записка 8–12 страниц, одностраничное сравнение, презентация до 12 слайдов, схемы, бюджет/дорожная карта, реестр рассчитанных рисков и интересов сторон, сохранённые планы и проверяемые выгрузки. Числа берутся из тех же результатов, что видны в приложении. Передача на GitVerse — по постановке, если организатор не сообщил другой порядок. Основание: постановка, с. 12–14.

Оптимизатор и бонусный ценовой модуль не должны задержать обязательную часть. Отсутствующий исходный XLSX остаётся вопросом сверки, но не мешает делать загрузчик, контракт данных и синтетические тесты; недостающие условия нельзя объявлять подтверждёнными.
